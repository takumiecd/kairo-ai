# モデル設計 (Model Design)

Kairo の変換モデルの設計方針をまとめる。実装の詳細仕様ではなく、**何を・なぜ・どの順で作るか**の指針。具体的なネットワーク構造は固定せず、実験しながら差し替えられる前提で書く。

## 基本方針

- 変換の出し方が異なる **2系統** を用意する（リアルタイム / 一発出力）。
- 役割で分けるだけで、各系統の**内部アーキテクチャは固定しない**（LSTM / Transformer / 非自己回帰などは差し替え可能にする）。
- まずは **1系統ずつ完成** させる。2系統を同時に作り込まない。
- モデルは「次トークンの確率」だけを持ち、探索・候補組み立てはデコーダ側が持つ（[`ROADMAP.md`](ROADMAP.md) の Model Boundary を踏襲）。

## 系統1: リアルタイムモデル（逐次出力）

タイピング中に、打った分から逐次的に変換結果を出し続けるモデル。ライブ変換・矢印キーでのbeam候補選択など、**入力途中のUX**を担う。Kairo の主役。

### 構造（RNN-T を基本形とする）

```
入力ローマ字 ──▶ [Encoder]      : 入力列 → 特徴量
出力済み日本語 ─▶ [Prediction]   : 既出力の文脈 → 次文字の手がかり
                       └──▶ [Joint] : 両者を結合 → 次トークン分布（<blank>含む）
```

- **Encoder**: タイプされたローマ字を特徴量に変換する。入力は確定済みなので**未来を見てよい（双方向）**。
- **Prediction Network**: これまで出力した日本語（過去の文脈）を読み、次に来る文字を予測する。**逐次生成**なので、各時点で「それまでに出した文字」しか見てはいけない。
- **Joint Network**: Encoder と Prediction の出力を結合し、「次の出力文字」または「`<blank>`（これ以上出さない＝次のタイプを待つ）」を予測する。

`<blank>` を含む次トークン確率を学習し、損失は `torchaudio.functional.rnnt_loss`（[`train/rnnt/loss.py`](../train/rnnt/loss.py)）を使う。

### なぜ逐次生成か

日本語変換は曖昧で、前後の文脈で答えが変わる（例: `kisha` → 記者 / 汽車 / 貴社）。だから前の出力を見ながら1文字ずつ決める。この「前の出力を読む係」が Prediction Network。

### アーキテクチャ差し替えの方針

現状は Encoder / Prediction とも LSTM（[`model/transducer.py`](../model/transducer.py)）。Joint と損失・デコード経路はそのままに、Encoder/Prediction の中身だけ差し替えられるようにする。

**推奨の進め方**:
1. Encoder だけ Transformer 化し、LSTM版と切り替え可能にする（A/B比較・ロールバックが楽）。
2. `train.rnnt.overfit` で smoke test → 同データで CER を比較。
3. 効果が出たら Prediction も Transformer 化。
4. 最後に推論キャッシュ（Encoder出力の再利用・Prediction の差分計算）で高速化。

### Transformer 化で必要になるマスク（重要）

LSTM は構造上これらを暗黙に満たすが、Transformer は明示しないと壊れる。

| マスク | 目的 | Encoder | Prediction |
|--------|------|:------:|:----------:|
| **padding mask** | バッチ整形で詰めた `<pad>` を無視する | 必要 | 必要 |
| **causal mask** | 未来のトークンを見せない（カンニング防止） | 不要 | **必要** |

- **padding mask**: 長さの違う文をテンソルにまとめるため `<pad>` で埋める。これを無視させないと Attention が埋め草に注意を奪われ精度が出ない。`src_key_padding_mask` に `(x == pad_id)` を渡す。
- **causal mask**: 学習時は高速化のため正解列を丸ごと流す（teacher forcing）。マスクが無いと「次の文字」を決める瞬間に正解の続きが見えてしまい、推論時（1文字ずつ伸ばす）と挙動がズレて精度が崩壊する。上三角を `-inf` にして防ぐ。

> Prediction を Transformer 化する場合は **両方同時に**かける。ここを外すと「学習は順調なのに変換が全然ダメ」という切り分けの難しい壊れ方をする。

## 系統2: 一発出力モデル（一括変換）

入力が一区切りついた時点で、文を**丸ごと一括**で変換・推敲するモデル。逐次生成ではないので causal mask は不要。padding mask は使う。

- **非自己回帰**（全位置を並列に出力）や**反復編集**など、丸ごと出すことに適した構造を想定する。
- 損失は逐次型とは別物（位置ごとの cross-entropy 等）。`rnnt_loss` は使わない。**逐次型の改造ではなく別の機械**である点に注意。
- 既存の試作: [`model/edit_refiner.py`](../model/edit_refiner.py)（Levenshtein-Transformer 風の反復編集）、discrete diffusion 実験（`train.diffusion`）。

## パーソナライズ: モデルは固定、プロファイルを入力に

ユーザー適応は**モデルの再学習では行わない**。パラメータ θ は全ユーザー共通・固定とし、外部のユーザープロファイル u（頻度・recency・明示的登録などの統計データ）をデコーダと（将来は）モデル入力に渡して適応する。定式化・プロファイルの中身・実装順序は [`PROFILE.md`](PROFILE.md) を参照。

- **段階A（先行実装）**: `decode/beam.py` でのスコア融合。母集団のデフォルト分布を基準に、プロファイル語彙のトライから候補スコア差分を規則計算する。学習不要・モデル無変更。
- **段階B（効果検証後）**: 全profileで共有する一つのモデルの中で、デフォルト経路とprofile transition由来の局所的なスコア差分を共同学習する。profileごとのLoRAや個別モデルは作らない。既存のPrediction Networkへプロファイル埋め込みを直接注入する実装は比較対象の実験として残す。

> **旧方針からの変更**: feedback による LoRA ローカル微調整（`train.rnnt.lora`、`model/lora.py`）は**廃止**。θ を動かすため破滅的忘却・モデル汚染を持ち込む。`feedback.jsonl` の収集はプロファイルビルダーの入力として存続する。

## 将来構想: パイプライン

2系統を別々の変換器として競わせるのではなく、**繋ぐ**のが本筋。

```
打っている最中  → リアルタイムモデルが即時変換（低レイテンシ）
   ↓
手が止まったら  → 一発モデルが結果を推敲（高精度化）
```

これで「realtime」と「高精度」を1つの流れで両立する。`edit_refiner` は元々「既存の変換結果を修正する」設計なので、後段として自然に嵌まる。

## 実装の優先順位

1. **リアルタイムモデルを1本完成させる**（逐次型・mask有り）。まず Encoder の Transformer 化から。
2. CER が満足いく水準になったら、一発モデルを後段に接続して推敲を足す。
3. その後に高速化（推論キャッシュ）とパイプライン統合。

一気に2本ではなく、**1本ずつ積む**。
